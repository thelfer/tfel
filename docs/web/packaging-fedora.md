The latest version of this document is always available at
<https://thelfer.github.io/tfel/web/packaging-fedora.html>.

This document describes how to create official quality `Fedora`
packages of `TFEL`/`MFront` for a new release, either to publish a
[COPR](https://fedora-copr.github.io/) repository, to attach binary
packages to a `GitHub` release, or to prepare a `Fedora` package
review. It is a complement to the general [packaging
document](packages.html) which deals with the binary packages generated
with `CPack`.

The packaging metadata is maintained in the
[`packages/fedora`](https://github.com/thelfer/tfel/tree/master/packages/fedora)
directory of the sources (see [issue
\#1468](https://github.com/thelfer/tfel/issues/1468) for the overall
strategy). It contains a single spec file and the `sources` file used
by `rpmbuild` and `mock`, so that `TFEL` can be packaged with the
standard `RPM` tool chain.

# Building the packages

## Install the build tools

On a `Fedora` system:

~~~~ {#tools .bash}
$ sudo dnf install -y rpm-build cmake gcc gcc-c++ gcc-gfortran \
  make python3-devel
~~~~~~~~~~~~~~~~~~~~~~

Only free packages are required: the default configuration of `TFEL`
has no external dependency. The optional interfaces to third party
solvers (`aster`, `abaqus`, `calculix`, `cyrano`, `zmat`, etc.) and the
private linear solver `tdls` are disabled, as they require
prerequisites which are not part of `Fedora`.

## Build from a release tag

The archive of the packaged release must be in `SOURCES/`; the
`update-release.sh` script downloads it and keeps the spec file and the
`sources` file in sync (it is the recommended way of bumping the
packaging to a new release):

~~~~ {#binary_build .bash}
$ git checkout TFEL-x.y.z
$ cd packages/fedora
$ ./update-release.sh x.y.z   # only if the archive is not in SOURCES/
$ rpmbuild --define '_topdir '"${PWD}" -ba tfel.spec
~~~~~~~~~~~~~~~~~~~~~~

This builds the sources package (`SRPMS/`, which embeds the archive)
and the binary packages (`RPMS/`).

## Build from a development checkout

The spec file always refers to a released version. To test the
packaging of unreleased sources, build the tarball of the working
tree, name it as the release archive it replaces, and override the
version:

~~~~ {#devel_build .bash}
$ mkdir -p packages/fedora/SOURCES
$ git archive --prefix=tfel-TFEL-x.y.z/ -o \
  packages/fedora/SOURCES/TFEL-x.y.z.tar.gz HEAD
$ cd packages/fedora
$ rpmbuild --define '_topdir '"${PWD}" --define 'tfel_version x.y.z' \
  -ba tfel.spec
~~~~~~~~~~~~~~~~~~~~~~

The `sources` file is only used to fetch archives which are not
already in `SOURCES/`: it may point to another version during such a
trial, which is harmless as long as the archive of the version being
built is provided locally.

## Reproducible builds

Reproducible builds against a clean `Fedora` root, with the build
dependencies installed automatically, are obtained with `mock`: first a
sources package (which embeds the tarball), then its rebuild in a
chroot:

~~~~ {#mock .bash}
$ sudo dnf install -y mock
$ rpmbuild --define '_topdir '"${PWD}" -bs tfel.spec
$ mock -r fedora-rawhide-x86_64 --rebuild SRPMS/*.src.rpm
~~~~~~~~~~~~~~~~~~~~~~

Without installing anything on the host, a container can be used
instead:

~~~~ {#container .bash}
$ podman run --rm -v "$PWD":/pkg:z -w /pkg fedora:rawhide \
    bash -c 'dnf -y install rpm-build && \
             rpmbuild --define "_topdir /pkg" -ba tfel.spec'
~~~~~~~~~~~~~~~~~~~~~~

# Binary packages

| Package | Contents |
| :-----: | :------- |
| `tfel` | shared libraries and licences (pulls `mfront`, recommends `mtest`) |
| `tfel-devel` | headers, unversioned library links, CMake configuration files, `tfel-config` |
| `mfront` | the `MFront` code generator and companion tools, its documentation and gallery |
| `mtest` | the `MTest` solver and its markdown documentation |
| `tfel-check` | the `tfel-check` validation suite and its test files |

Compiling the interfaces generated by `MFront` (`--obuild` option) or
running a behaviour with `MTest` requires a C++ compiler and the
`tfel-devel` package: both are `Recommends` of the `mfront` and `mtest`
packages, so that they are installed by default but can be
explicitly excluded.

The `python3-tfel` and `tfel-doc` packages are not built yet: the
install path of the python bindings and the `pandoc` based documentation
generation are shared open points with the
[Debian packaging](https://github.com/thelfer/tfel/issues/1466)
effort.

# Configuration options

The packages are built with:

- `-Denable-portable-build=ON`: `Fedora` forbids `-march=native` for
  the binaries it distributes,
- `-DTFEL_APPEND_VERSION=OFF`: unversioned install tree
  (`/usr/include/TFEL`, `/usr/share/tfel`) and conventional SONAMEs,
- `-DLIB_SUFFIX=64`: `TFEL` installs the libraries in
  `lib${LIB_SUFFIX}` rather than in the `GNUInstallDirs`
  `CMAKE_INSTALL_LIBDIR` directory, so the multilib directory has to be
  injected this way,
- `-Denable-fortran=ON`: the `Fortran` bindings only require
  `gcc-gfortran`, which is part of every build root.

# Tests

`ctest` knows thousands of tests, but the test executables are not
built by the default target and the `generic-*`, `mfront-*` and
`*_mtest` matrices require an installed tree, as they call
`tfel-config` and `mfront`. Those tests are run by the `GitHub Actions`
workflow which validates each release, and can be run on an installed
system with the `tfel-check` package.

The `%check` phase of the build therefore builds and runs the
self-contained unit tests of the libraries only, which takes a few
minutes.

# Updating the packaging for a new release

The `update-release.sh` script of the `packages/fedora` directory
downloads the tarball of a new release, checks its checksums and
updates both the version of the spec file and the `sources` file:

~~~~ {#update .bash}
$ cd packages/fedora
$ ./update-release.sh x.y.z
~~~~~~~~~~~~~~~~~~~~~~

One then has to update the `%changelog` section, to check that the file
lists still match the install tree of the new release, and to rebuild
the packages:

~~~~ {#after_update .bash}
$ rpmbuild --define '_topdir '"${PWD}" -ba tfel.spec
$ rpmlint tfel.spec RPMS/*/*.rpm SRPMS/*.src.rpm
~~~~~~~~~~~~~~~~~~~~~~

# Continuous integration and published packages

The [`fedora-release.yml`](https://github.com/thelfer/tfel/blob/master/.github/workflows/fedora-release.yml)
`GitHub Actions` workflow builds the packages in a `Fedora` container
and publishes them as assets of the `GitHub` releases:

- on every published release (tag `TFEL-x.y.z`): the source and binary
  packages of the release are attached to that release;
- every week: `master` and every `rliv-x.y` maintenance branch (one
  build per major and minor version) carrying the packaging metadata
  are built and published to rolling prereleases named
  `rpm-rolling-<branch>`;
- manually, for any branch or tag.

The weekly packages are experimental development packages; the version
they carry is the version declared by the branch, with a `.github`
suffix instead of the `.fcXX` suffix of `Fedora`, so that they can be
installed side by side with the official packages once they exist. The
unit tests of the `%check` phase are only run for the release builds
(`--with check`, versus `--without check` for the weekly builds).

This complements the [COPR](https://fedora-copr.github.io/) repository
and the `Fedora` official repositories, which remain the recommended
ways of installing `TFEL` (see the
[path to an official package](https://github.com/thelfer/tfel/tree/master/packages/fedora#path-to-an-official-package)).
